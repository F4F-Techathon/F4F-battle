# 3D 制作与桌面演示计划

## 1. 技术路线与已验证边界

本方案优先完成一个有完整交互的三人桌面演示。48 小时内，最大的风险是生成网格的关节拓扑和面部变形；先用一名角色验证全链路，再扩展到三人。精细高模保留为源资产，网页交付独立的优化版本。

Hyper3D 当前 MCP 暴露图像上传、模型生成、BANG 部件拆分、进度查询、等待和结果获取。没有公开给本会话的绑定、动作生成、面部 shape key 或口型接口。BANG 仅作为可选拆件步骤，不能代替骨骼绑定。工具接入已经验证，模型质量和可动性尚未验证。

| 环节 | 首选技术 | 选择理由 / 使用边界 |
|---|---|---|
| 2D 设计 | 内置 imagegen + 锁定母版与角色提示词 | 每次派生保留身份；人工审图控制跨视角漂移 |
| 3D 初模 | Hyper3D Rodin Gen-2.5 MCP | 一角一任务；Medium + Quad 小样优先，必要时提升 High；MCP 的实际参数范围为准 |
| 预演、修模、绑定 | 本机 Blender 5.1.2 | 已检测可启动；完成站位、拓扑、权重、面部与动作，不依赖另一个 DCC |
| 身体控制 | Blender Armature；Rigify 可选 | Rigify 是否启用仍待检查；可直接建立统一简化骨架，避免新增付费绑定依赖 |
| 面部 | 独立眼球/眉毛 + 简化嘴部形变 | 共用低复杂度面部模板；高风险区域手工整理，不指望自动四边面拥有合格口周拓扑 |
| 网页 | TypeScript + Vite + Three.js | 让人物、状态机、路径和音频时钟相互独立；接入现有前端时沿用其工具链 |
| React 团队适配 | React 19 + React Three Fiber 9 + Drei | 仅在团队采用 React 时选用；不在比赛期间切换到 alpha 版本 |
| 资产格式 | glTF 2.0 / GLB | 包含骨骼、贴图、动作和形变权重，避免重写模型为 Three.js 几何代码 |
| 播放 | 每角色一个 AnimationMixer | 身体 Action 混合；表情与口型通过独立参数控制，防止同一轨道被多个系统覆盖 |
| 气泡 | 跟踪 3D 头顶锚点的 HTML/CSS | 以 3D 位置为基准，文字保持可读，支持中文换行与可访问性 |
| 场景 | Blender 微缩地图 + 低复杂度场景 GLB | 三个餐馆地标、舞台、路径与灯光；首版无需全城高模、真实寻路或物理模拟 |
| 音频 | Web Audio + 统一口型适配器 | 跟随音频播放时间；可接 TTS 的时间戳事件，先用固定测试音频 |
| 优化 | glTF Transform、Meshopt、KTX2 按需 | 必须在优化前后检查骨骼、形变与材质；有问题先回退未压缩版本 |

Three.js 官方支持为独立对象使用独立 AnimationMixer，并提供动作淡入淡出；GLTFLoader 可加载 glTF 以及相应压缩扩展。[AnimationMixer](https://threejs.org/docs/pages/AnimationMixer.html)、[AnimationAction](https://threejs.org/docs/pages/AnimationAction.html)、[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)。React 版本组合依据 [React Three Fiber 官方说明](https://r3f.docs.pmnd.rs/getting-started/introduction)。压缩工具参考 [glTF Transform](https://gltf-transform.dev/)。

## 3. 动作表

所有共用动作先在统一骨架上制作，采用原地动画。网页控制世界位置和朝向；臀部保留上下弹跳，不在 clip 中重复写世界移动。

| ID | 动作 | 循环与建议时长 | 作用 |
|---|---|---|---|
| idle | 轻呼吸与重心变化 | 循环 3—5 s | 等待、倾听的身体基态 |
| run | 轻快小跑 | 循环 0.65—0.9 s | 从地图跑到舞台 |
| arrive | 刹停和小回弹 | 一次 0.6—0.9 s | 从移动过渡到站定 |
| wave | 小幅招手 | 一次 1.0—1.4 s | 出场或问候 |
| present | 摊手介绍 | 循环/分段 1.5—2.5 s | 说话时的基础手势 |
| point | 单手指向目标 | 一次 0.8—1.2 s | 指向证据卡或另一角色，不做攻击姿态 |
| nod | 点头认可 | 一次 0.6—0.9 s | 赞同用户/同伴 |
| disagree | 轻摇头并摊手 | 一次 0.8—1.1 s | 表达有依据的不同意见 |
| recoil | 小幅后仰后恢复 | 一次 0.6—0.9 s | 意外或被拆台 |
| celebrate | 小幅举手庆祝 | 一次 1.1—1.6 s | 被用户选中 |
| signature_sichuan | 叉腰扬眉、伸手邀约 | 一次 1.4—1.8 s | 四川老板娘个性 |
| signature_cantonese | 掌心慢推、礼貌邀请 | 一次 1.4—1.8 s | 粤菜老板个性 |
| signature_french | 小鞠躬后双掌展开 | 一次 1.4—1.8 s | 法式主厨个性 |

P0 播放策略：全身动作间交叉淡化；说话可同时驱动脸和视线。上半身 additive 层和精细动作遮罩列入增强项，以免首版出现腿部叠加与肩膀跳变。脚步频率按路径速度校准，不靠无限加速动画去追路线。

## 4. 骨骼与面部约定

基础导出骨架约 25 个节点：root、hips、spine、chest、neck、head；左右 shoulder/upper_arm/forearm/hand 共 8 个；左右 thigh/calf/foot/toe 共 8 个；jaw、eye.L、eye.R 共 3 个。四肢扭转骨按实测需要增加，目标上限 32。root 为定位节点，和变形骨职责区分。

骨骼名称、父子关系、静止姿态统一；三角色体型通过网格和有限比例调节体现。身材不同仍需逐角色检查肩、腋、胯和膝盖权重，不能仅改名字就认定可重定向。

身体：四指手整手驱动、裤装包住腿、短围裙附着于腰胯，尽量避免长裙、长围巾和布料模拟。帽子、发块、胸针、道具作为刚性附件或独立网格。

脸部：眼球独立，眉毛可用简化几何控制；嘴部重建简单可变形拓扑。建议最多 10 个表情形变通道 + 7 个非静止口型目标，Basis 不计入目标数量。眉毛也可以改为骨骼/独立对象，实际通道数在第一名角色样机后冻结。

需要优先解决口腔内部、嘴唇封闭与穿插。闭嘴参考图不会自动生成可用口腔。脸部情绪与语音口型共享嘴周时，由单一 FaceController 合成：语音主导开合，嘴角情绪适当衰减；不允许两个控制器轮流覆盖同一 shape key。

口型预设：rest、MBP、A、EI、O、UW、FV、L。它们是为卡通演示压缩的视觉类别，不等于八个字母，也不保证所有语言的精确发音覆盖。首版以普通话测试，其他语言另做映射与视觉验收。

## 5. 音频与口型路线

1. 文字夹具：用预计时长检验手势、气泡、表情和中断；不记为真实口型同步。
2. 固定音频：每段音频提供相对起点的 mouth cues，使用实际音频时钟播放。没有 cues 时，用音量包络控制嘴巴张合，标为近似口型。
3. 实时 TTS：语音模块向前端提供 audio chunk、序号、turnId、viseme 时间戳。时间戳换算在适配器统一进行，不以消息抵达时间直接触发表情。
4. 打断：停止该 turn 的音频，清除排队 cues 和手势，嘴回 rest，身体淡入 idle；迟到消息按 turnId 丢弃。

Azure Speech 是可选的带 viseme/audio offset 接口来源，不是本次绑定的采购或账号选择。不同语言/声音对事件和 blend shape 的支持需要逐项核对；SVG 口型在文档中限于 en-US。[官方 viseme 文档](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-speech-synthesis-viseme)。三位角色不必为接入同一动画协议使用同一个 TTS 供应商。

## 6. 从批准到交付的 pipeline

| 步骤 | 输入 → 操作 → 输出 | 放行条件 |
|---|---|---|
| A 2D 方向锁定 | 母版、角色设定表 → 用户审阅 → 版本冻结 | 配色、身份、比例、表情风格获得批准 |
| B Blender 灰模预演 | 简单人体和几何块 → 站位、镜头、路径、气泡空间 → 预演 .blend | 三条路线不冲突；三个脸和气泡在目标视口可读 |
| C 首名角色生成 | 独立四视图 → Hyper3D → 原始网格/贴图/任务 ID | 轮廓对齐；四肢分离；脸与嘴可修复 |
| D 首名完整可动样机 | 修模、必要重拓扑、UV、面部模块、统一骨架、权重 → 基础动作 GLB | 在浏览器完成 idle/run/present + 一个表情 + 口型测试 |
| E 另外两名角色 | 同规格参考 → 生成或共用基体适配 → 各自修模与权重 | 一致的骨骼和控制协议；保留个性，不复制同一张脸 |
| F 场景与完整动作 | 灰模舞台 → 材质、餐馆地标、共享动作、个性动作 → 完整 .blend | 表演和镜头不相互遮挡；道具按时间决定是否加入 |
| G 烘焙与导出 | 高模信息 → 优化网格和贴图；约束/IK 烘焙为动作 → GLB | fresh import 检查；无依赖 Blender 私有着色器、未烘焙驱动器 |
| H Three.js 测试 | GLB + manifest + 文本夹具 → 动作/表情/音频适配器 | 三角色独立播放，能打断、重置、重放 |
| I 多智能体接入 | 结构化事件 → 校验与调度 → 视觉状态 | 用户条件、事实来源、当前发言人与字幕一致 |
| J 演示封版 | 目标浏览器跑验收 → 固定版本、缓存、离线夹具 → 可交付包 | 性能记录、已知限制、备用演示脚本齐全 |

生成建议：先一名角色的 Medium/Quad 小样，quality_override 约 15,000—20,000 个生成多边形作为起点；这是生成参数，不是最终三角面预算。当前 MCP Quad 允许 1,000—50,000。必要时再用 High 追细节，保留低模绑定流程。不要一次生成三人合体模型，也不要将表情拼版混入建模参考。API 文档说明支持 1—5 张图且首图用于材质生成；具体可用选项以本会话 MCP 为准。[Rodin Gen-2.5 文档](https://docs.hyper3d.ai/en/api-specification/rodin-gen2-5)。

BANG 按需要拆帽子、头发或衣物，但先尝试 Blender 分离；BANG 会消耗积分且不保证拆分质量。任何付费生成超时先查询原任务，不自动重复提交。用户批准 2D 后，仍先以一名角色小样控制质量与返工。

导出约定：源工程以米为单位、Blender Z-up；GLB 使用 glTF 的 Y-up。人物统一前向为 glTF +Z，root 位于脚底中心，网页以独立 wrapper 控制路径。Blender 约束、驱动器和程序材质不直接作为运行依赖，动作和可见形变需烘焙/转换并在导出后检验。保留源 .blend 与未经压缩的 GLB 作为回退。

## 7. 48 小时排程与止损

这是工作窗口，不是要求连续工作 48 小时。用户审批等待、休息、服务队列和团队集成都会占用窗口；时间表是有风险的演示计划，不是质量保证。

| 窗口 | 主要工作 | 里程碑与裁剪 |
|---|---|---|
| 0—4 h | 2D 审阅、资产规格、事件协议；团队前端先用方块演员 | 锁定角色和三站位，主持方能发测试事件 |
| 4—8 h | Blender 灰模预演、整理单视图、首角 Hyper3D 小样 | 路线与镜头可读，拿到可修复初模 |
| 8—16 h | 首角拓扑、绑定、3 个关键动作、面部、GLB 到网页 | 必须至少一名角色完成真实播放闭环 |
| 16—28 h | 另外两角适配、共享动作补齐、场景材质 | 三人能进场、说话、倾听、切换表情 |
| 28—36 h | 招牌动作、气泡、选择效果、固定音频、打断 | 60—90 s 演示可反复播放 |
| 36—42 h | 与多智能体事件集成、性能优化、异常测试 | 目标浏览器记录结果；删除低价值效果 |
| 42—48 h | 修复、缓冲、缓存资源、备用脚本与录屏 | 封版后只修影响演示的错误 |

硬性止损：

- 到 16 h 若仍没有首角在网页中可动，则先用统一可控基体 + 生成服装/发型适配完成三人，减少逐角色重拓扑。
- 面部连续变形超过约 2 小时仍不稳定，首版改成可替换的卡通眼口贴片，并限制头部极端侧转；仍按相同 emotion/viseme 接口驱动。该版本属于近似卡通表现，不宣称完成精细面部绑定。
- 到 28 h 未完成三人基础动作，则先保留 idle/run/arrive/present/nod/disagree 六类，招牌动作与道具后置。
- 帧率不足先减阴影、贴图与场景装饰，再减面数；不牺牲可读字幕和用户打断。
- 在线服务不可用时，切换明确标识的虚构数据/固定对话演示；不把录制脚本标成实时智能体结果。

## 8. 专业资产的源文件要求

交付包应包含 concepts/、references/、blender/、exports/、textures/、animations/、fixtures/ 和 manifest。每次生成记录：generation_id、模型 tier、输入图版本、prompt、原始输出、人工修订、导出版本和当前审批状态。记录素材来源与许可信息；生成资产使用权限以账户和比赛规则为准，尚未验证具体活动条款。

模型源文件需保留：干净 rest pose、骨架、权重、UV、贴图、命名稳定的动作、面部控制映射、材质、物体挂点。帽子/道具的可拆装不应通过修改骨骼层级实现。主版本固定后，换装主要改网格和材质。

## 9. 性能预算与验收

初始目标：每角 15k—25k 三角面，<=32 个导出骨骼节点，2—4 个材质槽；每角 1K 或 2K 贴图。三角总角色约 45k—75k 三角面，场景约 20k—40k。每角压缩下载目标 3—6 MB，整套核心内容约 <=25 MB。实际内存与 GPU 成本不能由压缩文件大小推断，必须测量。

桌面 1440×900 目标平均约 60 fps、95 分位帧耗时 <25 ms；最低可用目标稳定 30 fps。限制 DPR 到 1.5—2，阴影优先一盏主光加简化接触阴影。具体设备、浏览器、网络与时间点在验收时记录；此处没有任何已达成的性能结论。

12 类测试：

1. 三角色地图出现、路径与到位完整，不穿地、不重叠、不明显滑步。
2. 三人轮流发言，发言者强调和姓名、字幕匹配。
3. 发言时另两人可以作非语言反应，嘴部不误动。
4. 中途更换情绪、手势、凝视目标，没有明显跳变或权重冲突。
5. 用户打断后声音及时停止；嘴部约 150 ms 回静止；迟到事件不复活旧回合。
6. 连续两次说话、重复 eventId、乱序消息仍只执行一次。
7. 空文本、超长中文、英文、数字、emoji 均能处理；长文本分页，不遮挡脸。
8. 音频加载失败、缺口型 cues、无语音权限有明确回退，不伪造精确同步。
9. 0/1/2/3 个候选都能排布；k>3 则排队或分批，首版不自动挤进舞台。
10. 用户选择后只选中一个角色；重新筛选可清理前一场所有状态。
11. 1440×900、1920×1080 与缩放后字幕/气泡可读，开启 reduced-motion 时减少跳动。
12. 冷启动、缓存重放和 10 分钟循环记录帧率、内存、加载异常；GLB 优化前后骨骼/shape key 不丢失。

三层验收分别记录：文件结构正确、Blender 中变形正确、实际浏览器交互正确。存在 GLB、成功导出或网页能打开，都不等于整体演示已通过。

| 网页整合方（需团队指定） | 页面、状态接入、音频播放、资源加载、选择操作 | 可运行桌面页面；3D 方提供 AvatarController 接口 |

本计划不预设数据/多智能体成员同时承担网页整合。若尚无前端负责人，建议由 3D 方维护一个独立 asset-lab，再由队友按事件协议嵌入主页面。
