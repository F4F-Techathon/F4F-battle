# 多智能体交互展示框架评估

检查对象：http://localhost:8770/#live。检查日期：2026-10-16。

结论：现有系统已经形成有辨识度的多角色实时表演层：角色、方言、语音、口型、表情、手势、旁听反应、会话恢复和决策检视均有实现。要成为可复用的多智能体交互展示框架，最需要补齐的是实际运行事件的接入、协作关系的可视化、任务状态与成果，以及可控制和可追溯的演示过程。

本次通过用户授权的无头 Edge 访问正在运行的服务，恢复既有 12 句会话，重播其中一句，并检查相关视图。隔离了检查浏览器的会话写入，避免覆盖原有自动保存。没有修改应用源码与设置。Jev 和改写服务当前为已配置，配音服务当前为 ready；本次没有重新执行全部远程模型生成及一致性验证，也未做麦克风、实际听感或完整无障碍测试。

## 已具备的基础

- 能即时把一条台词映射为角色表演，并有语音流、口型、字幕与旁听反应的时间协调。
- 有引用、排队、插话、停止、单句重播、保存、恢复、整场顺序播放。
- 决策检视器能展示表情等选项的分布、置信度、门控和人工覆盖。
- 有角色资产库、管线图、性能信息和与原片编排的一致性验证入口。

## 应优先补齐的能力

| 优先级 | 缺口 | 目前的依据 | 建议完成标准 |
| --- | --- | --- | --- |
| P0 | 实际智能体运行的接入与身份映射 | 主要入口是导演选择角色并填写台词；后端接口集中于改写、表演决策、配音与会话；没有看到通用运行事件接入接口 | 外部执行器可以创建一次运行，注册角色，并持续推送消息、任务、工具和状态事件；现有舞台作为一种渲染器使用 |
| P0 | 协作语义与因果关系 | 会话能引用另一句话；系统图是固定的处理管线，未呈现实际任务交接、定向消息、工具返回和结果汇合 | 点击一条消息可以高亮发送者、接收者、触发消息、对应任务和产生的结果；支持请求、答复、委派、质疑、接受、拒绝和总结等类型 |
| P0 | 任务、共享状态与成果展示 | 界面主要显示台词和表演标签；未见当前目标、需求约束、待办、决议和成果区 | 观众随时能看见本轮目标、各角色职责、已知事实与未解决问题；结束时出现可检查的结构化成果和来源 |
| P0 | 观众入口和交互编排 | 输入框让导演替选中的角色说话；主持人的需求收集、筛选与预订尚未在检查到的实现中形成对应流程 | 独立的用户输入入口；支持人工导演、自动执行和混合接管；展示谁申请发言、为何获准以及讨论何时结束 |
| P0 | 展示时钟与执行时钟分离 | 当前只有一位正在表演的角色和语音队列；智能体状态主要由当前表演推算 | 后台多个智能体可以并行工作；前台能看到思考、查询工具、等待依赖、准备发言、失败等真实状态，再由发言调度器安排音频与镜头 |
| P1 | 可复用的角色与场景配置 | 角色顺序、站位、视线关系、餐馆场景和部分管线在多个文件中固定 | 新场景只需一份配置；能增删角色，配置身份、声音、能力、外观和布局；参与人数变化时仍能工作 |
| P1 | 完整事件追踪和可复现回放 | 有会话保存与顺序重播；页面事件最多保留 160 条；序列化省略原始 turn id 和引用 ref | 保存带版本的事件记录、稳定消息关联、状态快照、模型与人工覆盖来源；支持暂停、逐事件前进、拖动定位和从某处创建分支 |
| P1 | 清晰的指标含义和协作评估 | 心动指数按 persuasion 等表演参数计算，吃瓜值按 drama 更新；系统验证衡量的是和手工编排是否一致 | 明确标注模拟指标；另外展示任务完成、约束满足、冲突是否解决、耗时及失败等结果；概率只解释对应表演选项 |
| P1 | 观众、导演与调试视图 | 技术事件和表演标签占据主界面；检查抽屉覆盖舞台；窄屏需越过事件区才到会话 | 观众模式强调角色、关系、字幕和成果；导演模式提供接管和编排；调试模式显示事件与模型信息；手机保留可见输入与精简舞台 |

框架接入事件建议至少包括：协议版本、runId、eventId、seq、time、type、agentId、from、to、messageId、replyTo、taskId、causeId 和 payload，并按事件类型定义必填字段。事件类型覆盖 agent.status、message、task、tool、artifact、state.patch 和 run.lifecycle。无需公开模型内部思维过程，展示外部可验证的计划摘要、动作、证据和结果即可。

推荐结构：外部智能体执行器 → 事件适配器 → 规范化事件记录 → 会话与共享状态 → 发言/表演调度 → 舞台、关系图、会话、成果区。

## 当前实现的两个具体闭环问题

1. 主持角色的标签声称支持需求收集、洞察和预订，但当前与其他角色使用相同的导演台词入口；需要把对应产品能力接入，或收窄界面标签。
2. Jev 可以给出 delivery，检视器也展示配音语气；当前 live 的配音请求只传 who、text 和 lang，没有把该 delivery 传给配音接口。建议把语气和强度与音频生成、缓存键、重播策略联动，并验证实际听感。

## 第一轮改造建议

先保留现有角色与舞台，以“用户提出预算、口味、距离约束 → 主持提取需求 → 三位角色回应 → 发现不满足约束的方案 → 主持归纳比较并产出可核查结论”为一条完整演示。用它打通事件接入、消息关联、共享需求面板与最终结果卡。完成标准是：观众无需打开调试抽屉，就能说出每位角色的职责、关键分歧、信息变化和结论依据。随后再做通用角色配置、回放定位和更多场景。
